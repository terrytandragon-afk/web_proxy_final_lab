\section{课题背景与功能分析}

\subsection{开发目的}

Web 代理服务器位于客户端和目标 Web 服务器之间。客户端将访问请求发送给代理，代理解析请求中的目标地址，代替客户端连接目标服务器，再把响应转交给客户端。由于请求和响应均经过代理，代理能够在建立上游连接前判断目标是否允许访问，也能够在收到明文响应后检查网页正文。该工作过程覆盖了 TCP 连接、HTTP 报文解析、访问控制、内容过滤和安全审计等网络安全基础知识。

本课题的开发目的包括三个方面。第一，完成题目规定的 HTTP 请求转发、指定域名拦截和网页关键词过滤功能。第二，通过 Socket 和 HTTP 协议解析理解正向代理的数据处理过程，并明确普通代理面对 HTTPS 加密流量时的可见性边界。第三，建立可管理、可验证和可审计的实验系统，使规则能够在运行期间修改，使每次放行与拦截都能够通过统计和日志进行说明。

\subsection{功能需求分析}

项目功能按照课程必做功能、系统管理功能和扩展访问控制功能进行划分。课程必做功能直接对应题目要求；系统管理功能用于解决规则如何修改、结果如何展示、行为如何追溯的问题；扩展访问控制功能用于体现代理服务器在实际网络安全场景中的使用方式。

\subsection{开发环境与技术路线}

系统运行于 Windows 环境，使用 Visual Studio Code 进行开发，主要编程语言为 Python 3。代理服务使用 \code{socket} 建立 TCP 监听与上游连接，使用 \code{threading} 为每个客户端连接提供独立处理线程，HTTPS CONNECT 隧道使用 \code{select} 实现双向字节转发。管理后端使用 Python 标准库中的 \code{ThreadingHTTPServer} 提供页面和 JSON API，管理前端使用 HTML、CSS 与 JavaScript 实现。

配置和规则使用 JSON 文件保存，规则变更使用 JSONL 逐行记录，访问事件写入结构化文本日志。客户端 IP 和 CIDR 使用 \code{ipaddress} 模块校验，域名通配符使用 \code{fnmatch} 匹配。该技术路线不依赖大型第三方框架，便于在课程报告中说明协议处理和策略判定的底层过程。

\section{系统总体设计}

\subsection{总体架构}

系统由代理服务、管理后端、管理前端、配置与日志存储、测试工具五部分组成。代理服务监听 \code{127.0.0.1:8080}，处理浏览器或命令行客户端发来的代理请求；管理后端监听 \code{127.0.0.1:8088}，向前端和命令行工具提供管理 API。两个服务共享运行状态，规则修改后能够立即影响后续代理请求。

\subsection{模块组成}

代理核心模块负责监听端口、解析 HTTP 请求、执行策略链、转发普通 HTTP 请求和建立 HTTPS CONNECT 隧道。规则配置模块负责读取配置文件、定义规则组、校验并标准化规则值。日志审计模块负责写入访问、拦截和错误事件，并提供查询、清空和 CSV 导出。证据模块负责读取批量测试生成的独立日志，在管理前端中重建最近验收统计。管理前端负责规则编辑、运行设置、统计、日志和规则变更展示。

\subsection{数据结构与配置模型}

运行状态对象保存当前配置、统计计数、访问排行、关键词命中排行、缓存、限流桶和规则变更历史。共享状态由线程锁保护，避免多个客户端线程和管理线程同时修改数据时产生不一致。

列表型规则包括域名黑名单、域名白名单、客户端 IP 黑名单、客户端 IP 白名单、URL 关键词、正文关键词和禁止方法。运行设置包括黑白名单模式、缓存开关与容量、代理认证、限流上限和时间窗口。规则变更后，系统同时更新内存配置和 JSON 文件，使修改立即生效并在重启后继续保留。

\subsection{请求处理流程}

请求进入代理后按照固定顺序处理。客户端 IP 规则最先执行，使无权使用代理的主机无法消耗认证和限流资源；认证通过后执行访问频率检查；随后检查请求方法、域名和 URL。前置策略通过后，GET 请求查询缓存，普通 HTTP 请求连接目标服务器并检查响应正文，CONNECT 请求建立加密字节隧道。最后更新统计并写入日志。

\section{核心功能原理、设计与实现}

\subsection{HTTP 正向代理与请求转发原理}

HTTP 正向代理的核心作用是代替客户端访问目标服务器。客户端直连网站时，请求行通常只包含路径；客户端使用代理时，请求行可以携带完整 URL。代理首先从请求行和 Host 请求头中解析目标主机、端口与路径，再建立到目标服务器的 TCP 连接。由于目标服务器接收的是普通 HTTP 请求，代理需要将完整 URL 改写为路径形式，并重新生成 Host 请求头。

系统在转发前删除 \code{Proxy-Authorization}、\code{Proxy-Connection} 等只适用于代理连接的请求头，避免代理凭据泄露给目标网站。系统设置 \code{Connection: close}，以连接关闭作为本实验中响应读取结束的明确边界；同时设置 \code{Accept-Encoding: identity}，使服务器尽量返回未压缩正文，便于关键词检查。

上游连接由 TCP Socket 建立。代理发送改写后的请求后持续读取响应字节，直到目标服务器关闭连接。成功响应经过正文过滤后返回客户端；目标连接失败时返回 502，目标连接超时时返回 504。该设计将请求解析、上游连接和响应回传组成完整的 HTTP 代理链路。

\subsection{访问控制策略链原理}

访问控制采用有序、短路式策略链。每项策略返回“允许”或“拒绝”以及稳定的原因字段。只要某项策略拒绝请求，后续策略和上游连接立即停止，代理生成拦截响应并记录原因。该方式能够减少无效网络访问，也便于统计不同类型的拦截。

客户端访问控制根据 TCP 连接的源地址判断谁可以使用代理。IP 和 CIDR 网段通过网络前缀计算判断成员关系，黑名单优先于白名单；白名单为空时不限制客户端，白名单非空时只允许匹配项。代理认证检查 \code{Proxy-Authorization} 中的 Basic 凭据；固定时间窗口限流为每个客户端 IP 保存计数和重置时刻。

目标访问控制依次检查请求方法、白名单模式、域名黑名单和 URL 关键词。域名匹配支持完整域名、父域名后缀和显式通配符。URL 关键词检查目标主机、路径和查询参数。策略原因使用 \code{domain_blacklist}、\code{client_ip_blacklist}、\code{url_keyword:...} 等稳定字段，使前端、日志和测试能够使用相同语义。

\subsection{网页正文关键词过滤原理}

URL 过滤检查客户端发出的请求地址，正文过滤检查目标服务器返回的内容，两者位于处理流程的不同阶段。正文过滤首先分离 HTTP 响应头和响应体，再读取 Content-Type 与 Content-Encoding。系统只检查 HTML、纯文本、CSS、JavaScript 和 JSON 等文本类型；二进制文件和压缩响应直接放行，避免把任意字节错误解释为文本。

对于可检查的响应，系统将正文解码并统一转换为小写，然后与正文关键词规则逐项比较。命中关键词时，原始网页正文不会发送给客户端，代理改为生成 \code{403 Forbidden} 提示页。提示页包含拦截原因、命中规则、请求方法、目标地址和客户端地址，因此浏览器中显示的内容能够直接说明过滤结果。

正文过滤仅适用于代理能够读取的明文 HTTP 响应。若网站使用 HTTPS，浏览器和网站之间的应用层数据经过 TLS 加密，普通 CONNECT 代理无法读取网页正文。

\subsection{HTTPS CONNECT 隧道原理}

浏览器访问 HTTPS 网站时，先向代理发送 CONNECT 请求，请求中包含目标域名和 443 端口。代理可以在建立隧道前根据目标域名执行访问控制。目标允许访问时，代理连接目标服务器，向浏览器返回 \code{200 Connection Established}，随后只负责双向转发加密字节。

系统将客户端 Socket 和上游 Socket 设置为非阻塞状态，使用 \code{select} 监视两端是否存在可读数据。客户端数据到达时转发给网站，网站数据到达时转发给客户端，并在连接关闭或长时间无活动时结束隧道。

CONNECT 隧道没有解密 TLS。代理能够看到目标域名和端口，看不到 HTTPS 内部路径、查询参数和正文。因此 HTTPS 域名拦截能够生效，HTTPS URL 路径和正文关键词过滤需要额外实现中间人解密和证书信任管理，不属于本项目的实现范围。

\subsection{缓存、认证与限流设计}

HTTP GET 缓存以“目标主机、端口和路径”组成缓存键，每个条目保存响应字节、状态码、创建时间和过期时间。请求到达时先检查条目是否存在且未过期；命中时直接返回缓存响应，未命中时连接上游。缓存容量达到上限时删除最早创建的条目。该设计能够通过第一次请求未命中、第二次请求命中的现象展示代理缓存效果。

代理认证使用 HTTP Basic 机制。认证失败时返回 407 和 \code{Proxy-Authenticate} 响应头；认证成功后才进入限流和目标策略。转发请求时删除代理认证头，保证目标网站不会收到代理账号密码。

限流采用固定时间窗口算法。每个客户端 IP 对应一个计数桶，桶内保存当前请求数和窗口重置时间。窗口内计数达到上限后返回 429，并记录剩余等待时间。认证挑战不消耗已认证请求额度，修改限流参数时清空旧计数桶，便于运行期间重新配置。

\subsection{动态规则管理与并发一致性}

规则可以通过管理前端、JSON API 或命令行工具修改。三种入口最终调用同一组后端规则操作，包括新增、删除、修改、查询和整组替换。后端先校验规则组，再按规则类型标准化输入。例如请求方法统一为大写，IP/CIDR 由 \code{ipaddress} 校验并转换为标准网络地址。

规则修改在运行状态对象的线程锁内完成。后端先更新内存配置，再把完整配置写回当前 JSON 文件，同时追加一条 JSONL 变更记录。新的客户端请求会读取最新配置，因此规则不需要重启代理即可生效。锁保证多个代理线程和管理线程并发工作时不会同时破坏共享配置、统计或缓存数据。

\subsection{日志审计与管理前端设计}

日志按照用途分为访问日志、拦截日志、错误日志和规则变更记录。每条访问事件包含时间、事件类型、客户端地址、请求方法、目标主机、路径、状态码和字节数。拦截事件额外记录策略原因，规则变更记录包含操作类型、规则组、旧值、新值和保存结果。

日志查询模块把文本记录解析为结构化字段，支持按日志类别、事件类型和搜索关键词查询，并能够导出 CSV。运行状态对象维护总请求、放行、各类拦截、正文过滤、HTTPS 隧道、缓存、认证、限流和字节数统计。管理前端通过 JSON API 获取这些数据，提供规则编辑、统计展示、日志详情和规则变更回显。批量测试使用独立证据目录，前端可以读取最近一次验收结果，避免测试日志覆盖当前运行数据。

\subsection{真实外网手工验收准备}

手工验收使用真实外网地址。URL 关键词和正文关键词验收必须使用明文 HTTP 网站，因为普通 CONNECT 代理无法读取 HTTPS 路径和正文。验收前启动代理和专用浏览器：

\begin{lstlisting}[numbers=none,language={}]
python src\proxy.py --config config.example.json
powershell -ExecutionPolicy Bypass -File tools\start_proxy_browser.ps1
\end{lstlisting}

关闭认证和限流干扰，并切换为黑名单模式：

\begin{lstlisting}[numbers=none,language={}]
python tools\rule_cli.py set mode blacklist
python tools\rule_cli.py set proxy_auth_enabled false
python tools\rule_cli.py set rate_limit_enabled false
\end{lstlisting}

Edge 访问 HTTP 地址时需要输入完整的 \code{http://}。如果浏览器自动升级为 HTTPS，应关闭“自动切换到更安全的连接”，否则代理只能看到 CONNECT 域名。

\section{项目开发总结}

\subsection{完成情况}

本项目完成了题目规定的 Web 请求转发、指定域名拦截和网页关键词过滤功能。代理能够解析 HTTP 代理请求并连接目标服务器，能够在连接目标服务器之前执行域名、URL、方法和客户端地址策略，也能够在收到明文 HTTP 响应后执行正文关键词过滤。

在基础功能之上，项目实现了 HTTPS CONNECT、GET 缓存、代理认证、访问频率限制、黑白名单模式、动态规则管理、管理前端、统计与日志审计。规则可以通过前端、API 和命令行修改，并立即作用于后续请求。自动测试与真实外网手工验收能够从响应、日志、统计和规则变更多个角度说明功能结果。

\subsection{存在问题与改进方向}

当前代理不解密 HTTPS 流量，因此无法检查 HTTPS 路径和正文。正文过滤主要面向 UTF-8、未压缩的文本响应，对其他字符编码、压缩响应、分块传输和大文件流式处理仍可继续完善。缓存和统计保存在进程内存中，重启后会清空；日志使用文件保存，在数据量较大时查询效率有限。

后续可以增加管理端登录、规则快照与回滚、SQLite 审计存储、定时规则和更完整的 HTTP 流式处理。HTTPS 内容检查需要在受控实验环境中设计证书生成、客户端信任和私钥保护机制，并明确其安全与合规边界。

\section{心得体会}

本项目的主要收获是将 HTTP 协议、TCP Socket 和访问控制策略结合成一个可以实际运行的系统。实现代理转发后，可以直接观察浏览器请求经过代理、被改写、转发并返回的过程；实现域名与正文过滤后，可以区分“请求发送前拒绝”和“收到响应后过滤”两种处理位置。

开发过程中，浏览器对本机地址的代理绕过、HTTPS CONNECT 的加密边界、PowerShell 与 CMD 的 JSON 引号差异，以及限流对浏览器附加请求的影响，都说明网络程序的验证需要结合协议行为和运行环境。通过为每个模块设计独立测试、日志原因和恢复命令，项目最终形成了可重复验证的完整实验流程。
